数据库敏感字段加密

这一轮的国密改造，要动数据库里的一列：用户卡券的密码。要求是加密存储，同时现有功能不能受影响。

这张表已经在线上跑了一段时间。发券、核销、对账、导给渠道方，全都在读写这一列，存量是长短不一的明文。

最后落地的改动集中在一个 TypeHandler 和一个定时任务上，业务流程本身没有改。

刷完存量之后，同一列出现了两种样子：

idcoupon_nopassword
1C202400018H2K9A
2C20240002SM4V1$k3Jd8...

上面那条还没轮到，下面那条已经加密了。

密码本该是哈希，这一列为什么必须可逆​

「加密存储」落到实现上要先拆开。常见的加密有三类，混着用是方案走偏的起点。

类别代表能否还原常见落点
哈希摘要MD5、SHA-256、SM3不能校验、摘要、密码（配慢哈希）
对称加密AES、SM4能，加密解密同一把密钥字段加密
非对称加密RSA、SM2能，公私钥一对签名、密钥交换

三类的差别不在强度，在能不能还原。非对称加密拿整列字段去加密，性能和密文长度都不划算，它解决的是密钥分发和身份问题。

国密改造一般按这三段配：SM2 管签名和密钥交换，SM3 管摘要，SM4 管数据加密。具体字段落到哪一段，取决于它要不要被读回来。

正常账号密码不该加密，该用慢哈希。OWASP 的密码存储备忘写得很直接，密码要用 Argon2id、bcrypt、PBKDF2 这类慢算法，每个密码单独加盐。MD5 和 SHA-256 这种快哈希不够用。

卡券密码是另一种情况。渠道方对账要导出原文，客服核对要能念给用户听，所以只能选可逆的对称加密。安全上这不是最优解，业务约束下它却是唯一能走通的一条。

顺便收一个误解：Base64 和十六进制不是加密。它们只把二进制换成可打印字符，谁都能解回来。本文密文外面套了一层 Base64，安全性全在 SM4 那一层。

先看这张表，再决定改哪一列​

示意表，真实表名和字段名换掉了：

CREATE TABLE coupon (
  id          BIGINT       PRIMARY KEY,
  coupon_no   VARCHAR(32)  NOT NULL,
  password    VARCHAR(32)  NOT NULL,   -- 要加密的列
  status      TINYINT      NOT NULL,
  create_time DATETIME     NOT NULL
);

加密之后这一列里会同时躺着明文和密文，所以编码必须能自证身份，光靠长度猜不出来。

字段长度要在加密前算好。SM4 分组 16 字节，明文按 PKCS5 补齐到整块，再 Base64。前缀占 6 个字符：

明文长度补齐后Base64 长度加前缀
6162430
16162430
20324450
32324450

原来的 VARCHAR(32) 装不下 50 个字符。上线前改成 64：

ALTER TABLE coupon MODIFY password VARCHAR(64) NOT NULL;

改列之前你先看一眼这列上有没有索引、有没有报表按它查询。表大的话，这条 DDL 本身也要排窗口。

前缀要能自证身份​

密文长这样，SM4V1$ 后面跟 Base64 串。具体字样每个项目不同，下面统一按这个写。

前缀干三件事：

  • 区分明文和密文，读的时候第一眼就知道走哪个分支；
  • 留版本位，将来换算法或者换密钥靠它分流；
  • 排障时看一眼，就知道这条数据被处理过没有。

还有一件必须验证的事：前缀不能和存量数据撞上。

存量是业务系统自己写进去的，谁也说不准有没有哪张卡的密码刚好以 SM4V1$ 开头。真撞上，解密逻辑会把一段明文当密文送进 SM4，出来的要么是乱码，要么直接抛异常。

上线前两条 SQL 就够：

SELECT COUNT(*) FROM coupon WHERE password LIKE 'SM4V1$%';
SELECT MAX(LENGTH(password)) FROM coupon;

第一条返回 0 才往下走。第二条拿来核对字段长度，跟上面那张估算表对一遍。

前缀的字样可以再挑挑。带上版本号，将来换算法或者轮换密钥，同一列里新旧两版能共存，解密按前缀分流。

想更稳一点，就让业务侧永远写不出这个串，比如把版本号夹在两个固定符号中间。判断标准只有一条：库里搜一遍，一条都不命中。

一个 TypeHandler 收口读写两端​

MyBatis 的 TypeHandler 是 JDBC 类型和 Java 类型之间的转换点，参数写入和结果读取都会经过它。加密逻辑放在这里，业务代码不需要知道密文的存在。

@MappedTypes(String.class)
public class Sm4TypeHandler extends BaseTypeHandler<String> {

    private static final String PREFIX = "SM4V1$";

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i,
                                    String parameter, JdbcType jdbcType) throws SQLException {
        ps.setString(i, encrypt(parameter));
    }

    @Override
    public String getNullableResult(ResultSet rs, String columnName) throws SQLException {
        return decrypt(rs.getString(columnName));
    }

    @Override
    public String getNullableResult(ResultSet rs, int columnIndex) throws SQLException {
        return decrypt(rs.getString(columnIndex));
    }

    @Override
    public String getNullableResult(CallableStatement cs, int columnIndex) throws SQLException {
        return decrypt(cs.getString(columnIndex));
    }

    private static String encrypt(String plain) {
        if (plain == null || plain.startsWith(PREFIX)) {
            return plain;                     // 已经是密文，不再套一层
        }
        return PREFIX + SmUtil.sm4(KEY).encryptBase64(plain, StandardCharsets.UTF_8);
    }

    private static String decrypt(String stored) {
        if (stored == null || !stored.startsWith(PREFIX)) {
            return stored;                    // 存量明文，原样返回
        }
        return SmUtil.sm4(KEY).decryptStr(stored.substring(PREFIX.length()),
                                          StandardCharsets.UTF_8);
    }
}

SmUtil 来自 Hutool，底层走 BouncyCastle，依赖里要把 bcprov 带上。Hutool 的 SmUtil.sm4 默认是 ECB 加 PKCS5 填充，跟前面的长度推算对得上。密钥固定 16 字节，SM4 的密钥长度没有可选余地。

两个判断分支兼容了全部历史数据。读的时候不带前缀原样返回，写的时候已经带前缀不再加密，定时任务中断重跑靠的就是这两行。

挂到字段上，别全局注册：

@TableName(value = "coupon", autoResultMap = true)
public class Coupon {
    @TableField(typeHandler = Sm4TypeHandler.class)
    private String password;
}

autoResultMap = true 不能省。MyBatis-Plus 文档里的原话是「jdbcType 和 typeHandler 属性如果不与 @TableName 中的 autoResultMap = true 一起使用，也仅在 update 操作时生效」。漏了这句，写进去是密文，查出来还是密文。

也不要用 <typeHandlers><package .../></typeHandlers> 全局扫描。MyBatis 文档自己写着，注册一个针对 String 的 TypeHandler 会覆盖掉所有 String 属性和 VARCHAR 参数的默认处理。本来是一个字段的加密，变成全站 String 字段的加密。

等值查询还能用，LIKE 不行了​

写入端是免费的。只要写入经过 MyBatis 映射到这个字段，TypeHandler 自动加密，业务代码一行不用改。

查询端不是。条件是明文，列里是密文，直接比永远不相等。XML 里要显式挂 TypeHandler：

<select id="selectByPassword" resultType="Coupon">
  SELECT * FROM coupon
   WHERE password = #{password, typeHandler=com.xxx.crypto.Sm4TypeHandler}
</select>

挂上之后能查到，因为 SM4 的 ECB 模式是确定性的，同样的明文配同样的密钥，出来完全一样。这个特性在查询这里是便利，到代价那一节会变成负担。

失效的查询要提前梳理一遍。LIKE '%...%' 查不到，密文里没有原文的字符序列。ORDER BY password 排的是密文的字典序，LEFT、SUBSTRING 这类字符串函数同理。

导出给渠道方的文件，在应用层解密之后再写，别指望下游能解。

存量数据靠一次定时任务​

存量刷新做成一个可重复执行的批量任务，上线时手动触发一次。

分页扫，逐条更新：

SELECT id, password FROM coupon WHERE id > #{lastId} ORDER BY id LIMIT 500;

读出来的是被 TypeHandler 解密后的明文，写回去再被加密，整个过程业务不参与。每批 500 条，记下最后一条 id，下一轮接着走，比 LIMIT offset 深翻页稳。

更新走 updateById 或者单条 UPDATE ... WHERE id = ?，别拼成一整条大 SQL。单条失败不影响其他行，重跑也只处理没处理的。

「要不要处理」交给 TypeHandler 自己判断。带前缀的直接返回原值，等于跳过。整个任务因此是幂等的，中断重跑、跑完再跑，结果都一样。

进度看一条 SQL：

SELECT COUNT(*) FROM coupon WHERE password NOT LIKE 'SM4V1$%';

降到 0，存量就算干净了。降不下去，多半是窗口期还有旧实例在写明文。

这才是容易出事的地方。定时任务在跑，应用同时在接流量，旧版本没下线的话新写入的还是明文。刷完一轮不代表刷干净，得等所有实例都换成新版本之后再补一轮。

顺序排成这样：

  1. 发新版本，写入加密、读取兼容，确认所有实例已更新；
  2. 触发刷存量；
  3. 复查 NOT LIKE 'SM4V1$%' 的计数，为 0 才算完；
  4. 观察几天，把任务停用。

代价​

第一个代价在确定性。同样的卡券密码，密文也相同，库泄露时一眼能看出哪几张卡的密码是一个。

ECB 本身也不适合超过一个分组块的消息。Rogaway 那篇模式评估里说的是，它不达成任何通用的安全目标。用它是因为这一列短、要支持等值查询，而且国密合规有硬要求。

第二个代价在密钥。密钥放配置中心或者环境变量，配置和库同时泄露，加密就等于没做。它挡住的是「只拿到一份数据库备份」这一类事故。

第三个代价在变更。换密钥要把全表重刷一遍。前缀里的版本号能让新旧两版共存，重刷本身跑不掉。

第四个代价在范围。这套做法只覆盖单表、少数几列、不需要模糊搜索的场景。多表里的同一份敏感数据、超大字段、历史归档表，都得另想办法。

什么时候不该用：

  • 字段根本不需要还原，换成 SM3 哈希，连密钥泄露都不怕；
  • 字段要模糊检索，得换成可搜索加密，成本高一个量级；
  • 表大到刷一轮要按天算，得配合归档分批。

回到那几行数据​

再查一次，两行的样子终于一致了：

C20240001  SM4V1$Kz3mQ8dTpR...
C20240002  SM4V1$Rb7nX2pLmK...

复查那条 SQL 留在监控里，每天跑一次，计数不为 0 就告警，然后停用定时任务。

下次再有敏感字段要处理，拷一份 TypeHandler，换个前缀，剩下的流程照抄。
