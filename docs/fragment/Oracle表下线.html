Oracle 无用表下线的安全步骤

背景​

一个运行十几年的老系统，不知道被多少被程序员为维护过，数据库涉及到表，更是没有人能够完整说出来每张表的作用。

然而要保证一个系统的纯净和可维护性，对一些历史老表的功能梳理，在所难免，尤其是如何去判断一张表，有没有再用，值不值得去下线，回收磁盘空间。

确定一张表有在用很简单，难就难在怎么去评估一张没有调用。

共享盘里有一张 Excel，二三十行，每行一个 schema.table。它来自前一轮数据库治理：这些表看上去没人用，但没人敢删。

我接手的第一个念头是把能删的挑出来。做了一轮才发现，活儿在别处：把「看上去没人用」变成「有证据地没人用」。

先搞清楚 Oracle 里什么在依赖什么​

一张表从来不是孤立对象。视图的定义里有它的名字，触发器挂在它身上，package 的存储过程里写着 FROM app.t_order_old。

更远的一层在别的 schema：有人建了同义词，有人拿了授权，隔着 schema 直接读。老系统跑上十年，这类访问方式比走接口的多。

依赖还是链式的。视图 A 建在表上，视图 B 又建在 A 上；触发器里调一个 package，package 里再读第二张表。你以为在下一张表，实际会让一串对象一起失效。

更要紧的是，字典里记下的只有编译期写死的引用。官方文档写得很直接：EXECUTE IMMEDIATE 'SELECT * FROM tab1' 不产生对 tab1 的依赖（Schema Object Dependency）。所以 DBA_DEPENDENCIES 查干净了，不代表干净。

还有两样东西不在那张依赖表里：同义词和授权。Oracle 的同义词指向的是名字，不是对象。这一点在改名的时候会咬人。

第一关：在代码里找它​

拿到表名，先去代码里搜。大写、小写、带 schema 前缀、不带前缀，都搜一遍。老系统里还可能有拼出来的表名，前缀加个日期后缀，这种只能靠前缀搜。

搜到了先别急着认定它在用，问一句：这段功能还在跑吗。停掉的功能，先把代码注释或删掉，让它彻底不上线，再回来谈表。还在跑的，就得改造，改完才轮到评估。

然后是关联系统。这张表可能根本不由本系统写，是别的系统连过来直接读。本系统代码干干净净，别人那儿还在用，这种漏判在跨 schema 的老库里太常见。

这一关只负责做减法。搜不到，只能说明「没有静态引用」，说明不了「没人用」。

第二关：看数据留下的痕迹​

表自己会留痕。写入的痕迹在两处。

DBA_TAB_MODIFICATIONS 记着自上次收集统计信息以来的增删改行数，以及最后一次修改时间。前提是表监控开着，STATISTICS_LEVEL 不是 BASIC。这份数据先在内存里，查之前刷一下盘：

EXEC DBMS_STATS.FLUSH_DATABASE_MONITORING_INFO;

SELECT table_owner, table_name, inserts, updates, deletes, timestamp
  FROM dba_tab_modifications
 WHERE table_owner = 'APP'
   AND table_name  = 'T_ORDER_OLD';

口径要看清：它的起点是上一次收集统计信息。统计任务定期跑，窗口就一直往后滚。它答得了「最近一个统计周期有没有人写」，答不了「最后一次写是哪一年」。

要追更早的时间，看 ORA_ROWSCN：

SELECT SCN_TO_TIMESTAMP(MAX(ora_rowscn)) FROM app.t_order_old;

没开 ROWDEPENDENCIES 的话这是块级 SCN，一个块里动过一行，整块的行都跟着「变新」。SCN 太老还会直接报 ORA-08181，保留期取 undo retention 和 flashback archive 里较长的那个，最少 120 小时。查出来报错，本身就是个信号。

读取的痕迹散在几个动态视图里。V$SEGMENT_STATISTICS 有段级的逻辑读和物理读，但从实例启动开始累计，重启就清零：

SELECT statistic_name, value
  FROM v$segment_statistics
 WHERE owner = 'APP'
   AND object_name = 'T_ORDER_OLD'
   AND statistic_name IN ('logical reads', 'physical reads');

V$SQLSTATS 能搜到带表名的 SQL 文本，它比 V$SQL 留得久，游标老化之后记录还在，但一样活在内存里，实例重启就没了。再往前翻要靠 AWR 的 DBA_HIST_SQLTEXT 和 DBA_HIST_SEG_STAT，那需要 Diagnostics Pack 授权，不是每个库都买了。

把这些查完，能得到一个诚实的结论：它们只能证明最近有人用过，证明不了最近没人用。 没有记录，可能真没人访问，也可能只是游标被挤出去了。

这就是为什么要开审计。

第三关：开审计，等一个业务周期​

审计是唯一能正面回答「这段时间到底有没有人碰它」的手段，所以判断以审计为准。前面两关的作用只是把清单筛小，因为审计有代价，不适合二三十张表一起开。

代价在哪：BY ACCESS 是每条语句一条审计记录。一张高流量的表，一天几十万条，AUD$ 和 SYSAUX 会被撑起来，I/O 也是实打实的。顺序只能是先用代码和数据把明显还在用的摘出去，剩下的才进审计。

传统审计的写法：

AUDIT SELECT, INSERT, UPDATE, DELETE ON app.t_order_old BY ACCESS;

前提是 AUDIT_TRAIL 不是 none，这个参数改完要重启才生效。12c 之后新建的库默认是统一审计，传统审计的开关对它无效，得先建策略再启用：

CREATE AUDIT POLICY audit_t_order_old
  ACTIONS SELECT ON app.t_order_old,
          INSERT ON app.t_order_old,
          UPDATE ON app.t_order_old,
          DELETE ON app.t_order_old;

AUDIT POLICY audit_t_order_old;

观察期内定期看一眼有没有记录进来，按用户和操作类型聚合就够：

SELECT username, action_name, returncode, COUNT(*) AS cnt,
       MIN(timestamp) AS first_seen, MAX(timestamp) AS last_seen
  FROM dba_audit_trail
 WHERE obj_name = 'T_ORDER_OLD'
 GROUP BY username, action_name, returncode
 ORDER BY cnt DESC;

统一审计改查 unified_audit_trail，字段换成 object_name 和 dbusername。

窗口里一条记录都没有，基本也就证明了挂在这张表上的 package 和触发器没在跑。到这一步，依赖清理才有底气往下做。

规定是观察两三个月，实际排期常常被上线压力压到一到两个版本。压缩可以，底线是这个窗口至少要跨过一次月结。真正容易漏的是每月一号的批处理、年末才启用的报表，日常流量反而好抓。版本号只是排期的单位，业务周期才是判断的单位。

摊开看大概是这样：版本 N 开审计，版本 N+1 或 N+2 改名，再下一个版本 drop。中间任何一步判断不过就退回去继续观察，多花一个版本，总比删错了再想办法强。

观察期里还有件事容易忘：审计记录自己在长。有些库配了清理策略，三个月后发现 AUD$ 早被 purge 过一轮，观察期白等。每周看一眼增量，比最后一次性查要靠谱。

把依赖挖干净，再动第一刀​

审计跑着的时候，正好把依赖理清楚。先从字典的静态依赖往下挖：

SELECT LEVEL, owner, name, type,
       referenced_owner, referenced_name, referenced_type
  FROM dba_dependencies
 START WITH referenced_owner = 'APP'
       AND referenced_name  = 'T_ORDER_OLD'
CONNECT BY NOCYCLE referenced_owner = PRIOR owner
       AND referenced_name  = PRIOR name
 ORDER BY LEVEL, owner, name;

NOCYCLE 不能省。两个 package 互相引用，或者视图绕成一圈，不加直接报 ORA-01436。

这张表只覆盖静态引用，动态 SQL 还得靠文本兜底，把全库源码扫一遍：

SELECT owner, name, type, line, text
  FROM dba_source
 WHERE UPPER(text) LIKE '%T_ORDER_OLD%'
 ORDER BY owner, name, type, line;

视图的正文不在 DBA_SOURCE 里，得单独查 DBA_VIEWS.TEXT，物化视图查 DBA_MVIEWS.QUERY。触发器虽然进了 DBA_SOURCE，正文被折成多行，按名字捞一遍更省事。调度作业的 JOB_ACTION 里也可能藏着表名，那是另一种动态 SQL。

再把跨 schema 的入口查一遍：

SELECT owner, synonym_name, table_owner, table_name, db_link
  FROM dba_synonyms
 WHERE table_owner = 'APP' AND table_name = 'T_ORDER_OLD';

SELECT grantee, privilege, grantable
  FROM dba_tab_privs
 WHERE owner = 'APP' AND table_name = 'T_ORDER_OLD';

外键查 dba_constraints，constraint_type = 'R'，用 r_constraint_name 对上这张表的主键或唯一约束。挂在表上的触发器查 dba_triggers 的 table_owner 和 table_name。

这些结果要落成两份文件，不是看一眼就算完：一份是「跟着一起下线」的对象清单，视图、package、触发器、同义词逐个确认调用方也停了；一份是回滚脚本，把这些对象的 DDL 原样存下来。

DDL 用 DBMS_METADATA 导，数据和元数据用 Data Pump 按表导：

SELECT DBMS_METADATA.GET_DDL('TABLE', 'T_ORDER_OLD', 'APP') FROM dual;
SELECT DBMS_METADATA.GET_DEPENDENT_DDL('OBJECT_GRANT', 'T_ORDER_OLD', 'APP') FROM dual;
expdp system/****** DIRECTORY=dpdir DUMPFILE=t_order_old.dmp \
      TABLES=APP.T_ORDER_OLD CONTENT=ALL LOGFILE=t_order_old.log

备份齐了，第一刀只改名，不删：

ALTER SESSION SET DDL_LOCK_TIMEOUT = 60;
ALTER TABLE app.t_order_old RENAME TO t_order_old_bak_202603;

改名这一下，动的和不动的东西必须分清楚。

数据、索引、约束、触发器、授权都跟着表走。它们在字典里挂的是对象号，rename 只换名字，这些都不丢。

视图、物化视图、package、存储过程里对它的静态引用会被标成 INVALID。真正的报错不发生在改名那一刻，发生在它们下一次被调用的时候，可能是明早，也可能是下个月一号的批处理。

同义词不会跟着改。它指向的还是 APP.T_ORDER_OLD，这个名字已经不存在，走同义词进来的调用报 ORA-00980 或者 ORA-00942。

这就是第一版只改名的全部意义：错误是可观测的，回滚是一句话。

ALTER TABLE app.t_order_old_bak_202603 RENAME TO t_order_old;

改回来之后把失效对象重编译一遍，DBMS_UTILITY.COMPILE_SCHEMA('APP') 或 UTL_RECOMP，再看 dba_objects 里有没有 INVALID 残留。rename 要排他锁，所以放在能盯着的时间点做，别在周五下班前改完就走。

第二个版本才 drop​

改名之后挂一个版本。这期间没有新的报错冒出来，dba_objects 里也没有 INVALID 爬起来，才轮到第二刀：

DROP TABLE app.t_order_old_bak_202603 PURGE;

PURGE 不能省。不加的话表进回收站，空间照样占着，还能 FLASHBACK TABLE 回来，等于没下线。

drop 完 datafile 也不会自己变小。段释放的是表空间里的空闲区，文件尺寸是另一回事。要真把磁盘还回去，先看 dba_free_space 和 dba_data_files，确认空闲区够用、高水位允许，再 ALTER DATABASE DATAFILE ... RESIZE，或者对表空间做 shrink。

数据要留的走归档，不留表。expdp 导成文件扔进归档盘，或者用 sqoop 打进大数据表。归档做完表照样 drop，两件事不冲突。

顺便纠一个说法：这里释放的是硬盘空间。drop 一张表不会让 SGA 变小，Buffer Cache 该怎么用还怎么用。

代价​

这套流程的成本不在 SQL 上。

AWR 那部分视图要有 Diagnostics Pack 授权。没有授权的库只能靠 V$ 视图加审计，回溯能力差一截，观察期就得更谨慎。

审计本身有开销，观察期越长开销越大。压到一两个版本能省钱，代价是可能漏掉一年才跑一次的作业，这类漏判要等到下一个年末才暴露。

盲区一直在。别的库通过 DBLink 连过来读、外部程序直连、批处理里拼出来的 SQL，字典里都看不见。审计能兜住大部分实际发生的访问，兜不住的是「这几个月恰好没跑」。

rename 的报错发生在下次被调用的时候，所以改名的时机比改名的动作重要，最好排在能盯住一整个批处理周期的位置。

还有些表不能删，跟使用频率无关：合规要求留存数据。这类应该走归档，不该混进下线清单。

反向的坑也有。没数据的表不等于能删，配置表和字典表可能一年写一次、每天读一万次。审计期里它一定很热闹，热闹得让你不敢删，这是对的。

回到那张表​

那张 Excel 的最后是逐行画掉的。改造完的在备注里写「已改造」，归档的写「已归档」，rename 观察中的标上版本号，drop 完的画一条横线。

清单也比一开始多了几列：最后写入时间、依赖对象数、审计结论、处置方式、执行版本。二三十行变成这样，才算把「看着没人用」变成了「有证据地没人用」。

drop 只是最后一条语句。
