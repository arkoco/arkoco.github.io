Mycat 的自增主键挡住了回滚

Mycat 的 schema.xml 里，分片表可以挂一个 autoIncrement="true"。挂上之后，主键不再由 MySQL 生成，改由 Mycat 的全局序列发号。

用哪种发号方式在 server.xml 的 sequnceHandlerType 里选：0 是本地文件，1 是数据库表，2 是时间戳，还有两种走 ZK。

这套东西在分库分表里是必需品。分片之后 AUTO_INCREMENT 只在单个分库内唯一，跨库会撞，号只能由中间件统一发。

迁到 OceanBase 的时候，它变成一个障碍。

先改主键，再谈链路​

OceanBase 有一条硬规定：分区表的主键必须包含分区键。Mycat 的分片表主键通常只有一个 id，分片键是另一列，比如门店号、订单号。

这两列在 MySQL 里可以分开，在 OB 里不行。官方最佳实践给了两条路：

  • 把分区键并进主键，做成复合主键。前提是分区键非空，很多老表是 DEFAULT NULL，得先确认能不能去掉。
  • 保留原主键，另建全局唯一索引兜底。全局索引是独立的数据结构，高并发下有性能瓶颈。

这一步和发号器无关，但顺序有关：表结构定不下来，反向链路就没法配。

号段账本不在数据库里​

数据库方式的发号，账本是一张表，MYCAT_SEQUENCE，放在某个分库上。Mycat 一次向它申请一批号段，比如 100 个，缓存在自己内存里，用完再申请下一批。

号段的消耗只发生在 Mycat 那一侧。数据库里那个 current_value 只在申请时往前走。

反向链路搬的是数据。它按迁移对象清单同步表，账本表如果不在清单里，OB 那边写了多少条，它都不知道。

这就断开了。OB 用自己的自增列发号，号从 1 开始，或者从表里的最大值往后走；Mycat 的账本停在切换那一刻。

回切的时候账本还是旧的​

正常情况用不上回退。切到 OB 跑上一两周，没异常，把 MySQL 和反向链路一起下线，这套账本也就没人看了。

真出问题要切回去，顺序是：停写、等追平、停反向链路、两端校验，然后把流量指回 Mycat。

问题在这一步。Mycat 重启后从账本里读到 current_value，接着往下发，而这些号在 OB 期间已经被用掉了。新写入的数据要么主键冲突插不进去，要么把 OB 期间那条记录覆盖掉。

所以搭反向链路之前，先把 Mycat 的自增关掉。号只从一个地方出，账本才不会分裂。

关的方式看版本。Mycat2 的建表语句里带 AUTO_INCREMENT 就走全局序列，去掉关键字就回到 MySQL 自增；1.x 要改 schema.xml 的 autoIncrement，再处理掉对应的 sequence 配置。

代价​

关掉之后得有人接手发号，没有免费的方案。

交给 MySQL 的 AUTO_INCREMENT，回切之后能自增，但分片之间会撞号，等于把当年分库分表要解决的问题又请回来。

交给应用发号，就得改代码，还要保证新发的号大于历史最大值。雪花这种不依赖号段的方案最稳，代价是 ID 变长，老代码里按位数判断 ID 类型的地方会跟着出问题。

留在 OB 侧发号、再想办法让 Mycat 的账本追上，只在回切窗口很短的时候成立。窗口一长，追账本本身又是一件事。

单库迁移要改的那几处，在 兼容不等于不用改。

回到那行配置​

schema.xml 里那个 autoIncrement="true"，在迁移清单上很不起眼。它不在任何一张 SQL 兼容性表里，也不会有对应的报错。

它决定的是，出问题那天，你能不能切回去。
