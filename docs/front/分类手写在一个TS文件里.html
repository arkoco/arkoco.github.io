分类为什么手写在一个 TS 文件里

src/data/categories.ts 里有这么一行：

{docId: 'fragment/scoop/scoop', label: 'Scoop 包管理', date: '2026-08-03'},

全站十几篇文档的顶栏、侧边栏、首页「最近更新」，都是从这类行算出来的。这个文件一百四十多行，是仓库里唯一写死分类的地方。

autogenerated 只认文件夹​

Docusaurus 可以从文件系统生成侧边栏：一个文件夹变成一个分类，一个文件变成一条文档链接。默认排序是文件名的字母序，sidebar_position 只在自己那一层里起作用（官方文档）。

本仓库的 docs/fragment/ 是反例。IDEA 调试技巧、Git Bash 配置、npm 代理、快速删除包、Scoop、SQL 脚本、Linux 代理、iPhone 壁纸，八个文件全躺在同一层。

autogenerated 会把它们按文件名排成一列：IDEA调试技巧、Iphone设置动态壁纸、git bash 配置、linux代理配置，读者从这一列里看不出「开发工具」「系统配置」「数据库」的界线。

要拆，最顺手的办法是建目录、搬文件。这个站点没有给任何文档设 slug，URL 由文件路径推导，搬一次就是改一次线上地址，所有入链跟着断。

一份数据喂三处​

categories.ts 里每个分类有两份列表，这是有意的：

字段谁读它形状
docs首页平铺，一篇一行
groups侧边栏按主题分组
date首页「最近更新」倒序取前 5

顶栏只取 key，换成 docSidebar 的 sidebarId，点进去落到该侧边栏的第一篇。首页要得更多：总篇数、每个分类的篇数、分类行点进去的落点，全靠 docs。

这段关系还有一面：这份表只管导航，不参与 URL。改 label、改分组、把一篇从「开发工具」挪到「系统配置」，线上地址都不动。

侧边栏那一处也是派生的，sidebars.ts 全文不到三十行：

const sidebars: SidebarsConfig = Object.fromEntries(
  categories.map((category) => [
    category.key,
    category.groups.map((group) => ({
      type: 'category' as const,
      label: group.label,
      items: group.docs.map((doc) => doc.docId),
    })),
  ]),
);

跑完 npm run build，四个分类各自成为一个 sidebar，frontSidebar、devToolsSidebar、systemSidebar、databaseSidebar，和顶栏的四个入口一一对应。加一个分类只改这一个文件，三处不会各自跑偏。

重复收录换来一条 -1 路由​

改造前的 sidebars.ts 是这样的：

tutorialSidebar: [{type: 'autogenerated', dirName: '.'}],
frontSidebar: [{type: 'autogenerated', dirName: 'front'}],
fragmentSidebar: [{type: 'autogenerated', dirName: 'fragment'}],

'.' 已经覆盖全部文档，'front' 又把 docs/front/** 收了一遍。这条 tutorialSidebar 是 create-docusaurus 模板自带的默认值，建站时没删，后来加 frontSidebar 时重叠就出现了。

把这三行放回去跑一次构建，.docusaurus/routes.js 里会同时出现两条路由：

/docs/category/dinosaurs-网站配置
/docs/category/dinosaurs-网站配置-1

重复的是分类索引页，不是文档页。文档页各自只有一条路由。

原因在 docs/front/dinosaurs/_category_.json 里那句 link: {type: 'generated-index'}：同一个文件夹在两条 autogenerated 侧边栏里各生成一次索引，第二份就带上 -1 后缀。

把 frontSidebar 改回现在这种显式分组，这条路由就没了。

tutorialSidebar 从来没被顶栏引用过，照样被渲染。侧边栏不是「被人点开才存在」的东西，写进 sidebars.ts 就会生成条目和分类页。

官方对「同一篇文档进两个侧边栏」的说法很直白：Docusaurus 不保证浏览它时显示哪一个（Using multiple sidebars）。这份重叠不算 bug，是自己配出来的。

能构建不等于读者能到​

docs/temp/linux系统变量配置.md 曾经就是这样：不在任何 sidebar 里，构建全绿，页面也能直接访问，但站内没有任何入口。

官方文档写得清楚，文档没有关联侧边栏时，也不生成上/下一篇。页面在，读者到不了。

官方把这种做法叫双向绑定：把文档 Y 加进侧边栏 X，浏览 Y 时就会显示 X。反过来也成立，任何侧边栏里都没有 Y，Y 就没有归属。

现在它被显式收进「系统配置」的 Linux 组，文件没动，URL 没变。分类表里多一行就恢复了可达性，这是手写换来的直接好处。

代价都记在双写上​

双写是笔实账。docs 本身是 groups 展平后的副本，只给首页用；同一篇文档要在两处各写一次，漏一处就是「首页有、侧边栏没有」，构建不会提醒。反过来漏在 docs，页面就变成能访问、没入口的那种。

docId 是纯字符串。写错一个中文字，npm run typecheck 照样通过，因为 tsc 只检查它是 string。

date 也是手写的。CI 用 actions/checkout 的浅克隆，所有文件时间会被压成 checkout 那一次，从 git 读不到真实的更新时间，所以日期只能跟着文档一起改。

新建文件夹也不会自动出现在导航里。现在十几篇，手工维护是几十行；哪天涨到一百多篇，每次新增都要在正确的位置插一行，这笔账就反过来了。

到那时该改回去：用 _category_.json 管文件夹、让 autogenerated 生成骨架，再写一个 sidebarItemsGenerator 在默认结果上重排或过滤。官方示例里的 reverseSidebarItems 就是十几行。

那一行看着像写重复了​

那行 docId 写的是 fragment/scoop/scoop，看着像写重复了。实际路线是：目录叫 scoop，文件也叫 scoop.md，Docusaurus 会把重复的片段折叠掉，真实地址是 /docs/fragment/scoop。docId 仍然要写完整路径。

所以首页「最近更新」那几行不能拼 /docs/${docId}，得用 useDocPath 去读 Docusaurus 算好的 doc.path。useDocById 帮不上忙，它只返回 id、title、description、sidebar 四项，没有 permalink。

加一篇新文档的动作是固定的：写 md，在 categories.ts 的 docs 和 groups 各加一行，label 写中文、date 写 YYYY-MM-DD，然后跑 npm run typecheck && npm run build。

构建绿了，首页「最近更新」会按 date 把它排进去；漏写 date，它会排到末尾并显示一个短横线。
